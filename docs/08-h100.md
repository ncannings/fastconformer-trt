# NVIDIA H100: controlled headline and the Hopper kernel retune

On a rented H100 SXM (sm_90), fastconformer-trt runs parakeet-ultra at **20,667x real time**, 4.4x stock NeMo on the
same GPU (4,693x), at the same accuracy (test-clean 1.841% vs 1.795%, Earnings-22 10.09% vs 10.06%), and uses
**119 J of GPU energy per hour of audio against 299 J** for stock NeMo.

This machine was also used to retune our CUTLASS kernels for Hopper.

## Setup

- One NVIDIA H100 80GB HBM3 (SXM) on RunPod: 700 W power limit, max SM clock 1,980 MHz, driver 570.211.01, compute
  capability 9.0.
- The machine is the `nvcr.io/nvidia/nemo:25.11` container (x86-64), run natively as on the B200
  (`engine/cloud_tune_native.sh`).
- Plugins built with `FC_SM=90`. Data: LibriSpeech test-clean (2,620 utterances) and the full Open ASR Leaderboard
  Earnings-22 test set (2,741). FP8 calibration on English only.
- Controlled headline: stock and engine run back to back on the same GPU, with GPU power sampled by `nvidia-smi`
  during each timed window (there is no wall meter in a cloud machine, so these are GPU-only joules).

## Retuning our kernels for Hopper

Our CUTLASS kernels were tuned on the Spark's GB10. On Hopper they ran at under 400 TFLOP/s, against roughly 1,000 for
cuBLAS. Two changes were made, both selectable at run time or build time:

1. **Hopper kernel variants** (`FC_SM=90` only): larger tiles, 2-CTA clusters and warp-specialised TMA epilogues,
   selected per GEMM with `FFN_V1`, `FFN_VR`, `SPL_VR` and `QKV_V` and chosen by `plugins/sweep_kernels.sh`.
2. **FP8 fast accumulation**, which cuBLAS also uses: the Hopper mainloop schedules accumulate FP8 products without the
   periodic promotion to full FP32. `FC_FP8_PRECISE=1` at build time keeps the promoting schedules.

Unit tests at the encoder's shapes (6,400 rows), `results/h100/sweep_*.jsonl` and `fa_sweep_*.jsonl`:

| Kernel | Spark tiles | Best Hopper variant, fast accumulation |
|---|---|---|
| Feed-forward block with residual (two FP8 GEMMs, fused epilogues) | 0.282 ms, 380 TFLOP/s | **0.156 ms, 687 TFLOP/s** |
| Feed-forward GEMM1 alone | | 0.175 ms, 613 TFLOP/s (variant 8: 128 x 256 tile, 2-CTA cluster) |
| Feed-forward GEMM2 with residual | | 0.174 ms, 618 TFLOP/s (variant 13) |
| Dense residual linear (1,024 x 1,024) | 0.032 ms, 417 TFLOP/s | 0.023 ms, 589 TFLOP/s (variant 13) |
| QKV projection, heads-first | 0.178 ms, 226 TFLOP/s | 0.064 ms, 625 TFLOP/s (variant 8) |

Relative error of the combined feed-forward block is 2.3e-3 (1.0e-3 before), inside the 5e-3 acceptance limit.

## Does it change the engine?

No. The fused engine (all our plugins) against the datacentre configuration (TensorRT GEMMs plus RelPosAttn and
SubConv02), same runner, `results/h100/race*.json`:

| Engine | Encoder batch (ms) | RTF | test-clean | Earnings-22 |
|---|---|---|---|---|
| Fused, Spark tiles | 23.5 | 16,072 | 1.827 | |
| Fused, Hopper variants + fast accumulation | 17.7 | 20,070 / 19,814 | 1.812 | 9.994 |
| **Datacentre configuration** | **14.1** | **21,255 / 20,977 / 20,440** | 1.841 | 10.088 |

The retune closed most of the gap (fused engine 25% faster end to end) and accuracy is unchanged, but TensorRT's GEMMs
are still about 25% faster per encoder batch and 3 to 4% faster end to end. The datacentre configuration stays the
recommended Hopper build. End to end the difference is small because the TDT decoder (about 0.36 s per test-clean pass,
against 0.65 s for the encoder) now limits the pipeline, as on the GH200 and B200.
