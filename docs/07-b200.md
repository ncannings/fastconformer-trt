# NVIDIA B200: datacentre Blackwell

On a rented B200 (sm_100), fastconformer-trt runs parakeet-ultra at **25,073x real time**, 4.4x stock NeMo on the
same GPU (5,743x), at the same accuracy (test-clean 1.816% vs 1.808%, Earnings-22 10.05% vs 10.05%).

## Setup

- One NVIDIA B200 on RunPod (secure cloud): 183,359 MiB HBM3e, 1,000 W power limit, max SM clock 1,965 MHz, driver
  595.71.05, compute capability 10.0.
- The machine is itself the `nvcr.io/nvidia/nemo:25.11` container (x86-64), so everything ran natively without Docker:
  `engine/run_native.sh`, `NATIVE=1` builds, `engine/cloud_run_native.sh`.
- Plugins built with `FC_SM=100` (datacentre Blackwell schedules: 1-SM UMMA mainloop, TMA epilogue); the Triton
  attention kernel compiled on the machine.
- Data: LibriSpeech test-clean (2,620 utterances) and the full Open ASR Leaderboard Earnings-22 test set (2,741).
- FP8 calibration on English only. Default clocks, no heat soak, no energy measurement, five timed passes. As on the
  GH200, these are throughput figures at the GPU's default settings, not a controlled stock-machine comparison.

## Results

Ultra, `--batch 32 --max-batch 128 --dec-batch 256 --dec-bf16 --pipeline --pre-compile --fast-joint --fast-hyps` plus
the frame budget shown. Encoder time is trtexec's GPU compute for one batch of 32 sixteen-second utterances.

| Configuration | Encoder (ms) | Frame budget | test-clean | Earnings-22 | RTF |
|---|---|---|---|---|---|
| Stock NeMo | | batch 32 | 1.808 | 10.053 | 5,743 |
| Spark configuration (all our CUTLASS plugins, sm_100 build) | 15.0 | 9,600 | 1.825 | 10.084 | 23,118 |
| Datacentre configuration (TensorRT GEMMs + RelPosAttn + SubConv02) | 10.2 | 9,600 | 1.812 | 10.055 | 24,702 |
| **Datacentre configuration** | 10.2 | **19,200** | **1.816** | **10.053** | **25,073** |

The datacentre configuration is the GH200's T4 configuration:

```bash
MAXB=256 FFN_SKIP=1 LEAN_PREMASK_ONCE=1 LEAN_DWSHIFT=1 LEAN_RELSHIFT=1 LEAN_QKV=1 LEAN_ATTN_PLUGIN=1 LEAN_HB=1 \
  LEAN_POSCACHE=1 ./build_variant.sh ultra_dc
```

## Our kernels on sm_100

Unit tests at the encoder's shapes (6,400 rows), unchanged tile choices, `results/b200/unit_kernels.jsonl`:

| Kernel | Time | Throughput | Relative error |
|---|---|---|---|
| Feed-forward block with residual (two FP8 GEMMs, fused epilogues) | 0.130 ms | 823 TFLOP/s | 2.1e-4 |
| Dense residual linear (1,024 x 1,024) | 0.015 ms | 885 TFLOP/s | 2.1e-4 |
| QKV projection, heads-first | 0.031 ms | 1,298 TFLOP/s | 2.1e-4 |

The sm_100 port worked first time and is far better placed than our kernels on Hopper (384 TFLOP/s for the same
feed-forward block on the GH200). TensorRT's GEMMs still give the faster engine (10.2 vs 15.0 ms per batch), but end
to end the gap is 7%, because the pipeline is now partly bound by the decoder.

## What limits it

Per test-clean pass: encoder 0.57 s, decoder 0.34 s, preprocessing 0.03 s, overlapping to 0.78 s of wall time. The
TDT greedy decoder (thousands of small sequential steps) barely speeds up on a bigger GPU (0.38 s on the GH200, 0.34 s
here), so it is now the main limit on datacentre GPUs.

## Notes from the run

- A RunPod pod is a container, so SSH sessions do not inherit the image's environment. `cloud_run_native.sh` imports
  PID 1's environment (`PATH`, CUDA library paths and the `TRITON_*` tool paths); without the `TRITON_*` paths Triton
  cannot find `ptxas` and the compiled preprocessing and joint kernels fail.
- RunPod images must be x86-64; the NeMo 25.11 container is published for both architectures.
- Cost: about $6 for the session (two attempts, roughly 55 minutes of B200 time).
